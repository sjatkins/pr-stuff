### The binary record format (the core of everything)

Nearly all world, save, and player data is one hand-rolled binary format, not
text. It is a tagged-record stream: a 16-bit ID, then a payload whose size
depends on the field, repeated until a terminator ID (255 / 254 / 241).
Strings are a 16-bit length followed by raw bytes. Nothing is byte-swapped on
read, so the files are host-endian and tied to the struct sizes compiled into
the server.

The macros that define it live in `h/read.h` (`_Read`, `Read`, `ReadSD`,
`ReadAD`, `ReadRange`) and `h/write.h`. Every reader is a
`while (_Read(id)) switch(id) { case N: Read(field); ... }` loop with one
hard-coded case per field. The `Read` macro embeds the `break`, so the cases
look like fallthrough but are not.

- **Two schemes coexist.** Most loaders have the field IDs hand-coded per
  struct. A newer generic reader in `PRLib/Schema.c` walks a `Schema` table
  instead. The tables are in `PRLib/fields.c` (obj, mob, room, shop, race,
  sector, clan, item_set, skill, exit, char_data) and `PRLib/Effect.c`. Today
  only effects and the sector map sub-record are loaded through the schema
  reader; everything else still uses hand-coded switches, even though the same
  tables drive the compiler that writes the files.
- **Compressed fallback.** `pipe_or_file` in `PRLib/misc.c` opens the file,
  and if missing runs `zcat` on `<name>.<EXT>` through `popen`. Used for the
  world, mob, obj, shop, effects, race, clan and item-set files.

### The compilers that produce the binary files

- **`tran/tran.c`** is the main world compiler. It reads brace-delimited
  blocks (`ReadBlock`, `SubBlock`, `process_block`), supports `@macro`
  definitions, `#include`, `#define`, and `#offset`, and dispatches each
  `token param` pair through `parse_block` against the schema table for the
  file type. It writes the tagged binary via `h/write.h`. `tran_ruby.c` is a
  near-copy that can also dump Ruby; `dump.c` prints the schema.
- **`Zone/parser.y` + `scanner.l`**: yacc/flex grammar for zone reset files,
  driven by a list file, writing `zone.out`.
- **`AMPL/`**: a yacc/flex mob-program language. Nothing in the server
  references it; standalone and apparently unused.
- **`room2tran.c`**, **`Submit/submit.c`**, **`strip.c`** (build-time source
  scanner generating `h/fcns.h` and the proc table).

### What this means

- **Fragility:** no endianness handling, no versioning except in the player
  file, struct-size coupling. `h/write_swap.h` exists but nothing includes it.
- **Duplication:** field IDs are defined twice, once in `PRLib/fields.c` for
  the compiler and once as literal case labels in each hand-coded reader.
- **Zero validation on read:** most `fread` return values are ignored, and
  unknown IDs typically call `exit(1)`.

## 2. Runtime structures

**User:** so does game on startup parse all this into runtime memory structs?

**Assistant:** Yes. Everything the boot sequence reads is fully materialized
into in-memory C structs before the game accepts connections. There is no lazy
loading or on-disk lookup afterwards, with three exceptions.

Boot order from `db.c:boot_db`: text blurbs slurped into `char *` globals;
effects, classes, help index, zones, sectors, rooms, mobs, variables, objects,
then players. Rooms go into `room_db`, a hash table preallocated for 163,840
`room_data` slots. Mob and object prototypes go into `mob_db` and `obj_db`
hash tables of `index_mem`. Zones become a linked list. Races, sectors, clans,
item sets go into fixed arrays. `LoadWorld` and `LoadAutosaveRooms` replay
saved room contents. `boot_players` opens every file listed in `players.new`,
builds a temporary `char_data`, tallies limited items and gold, then frees it.

Not held in memory: help text (index of offsets only), story-teller files,
and player/account files (loaded on login, written on save).

Consequences: boot time scales with the whole world plus one pass over every
player file; the server never touches `.out` files after boot; the runtime
structs are the same layouts the binary format serializes, so `h/structs.h`
is effectively the file format.

## 3. Feasibility of JSONL per type

**User:** A goal I want to do is to take that parsing and create a jsonl file for each major type of struct that has an entry for each struct of that type as json eqivalent. Is that possible?

**Assistant:** Yes, and there is a shortcut already in the code. The `Schema`
tables in `PRLib/fields.c` carry, for each field, a name, a type code, a byte
offset into the struct, a size, and for enum and bitvector fields the string
list. That is exactly the metadata a generic struct-to-JSON writer needs.

Recommended approach: dump from the booted server via a `-dump-json <dir>`
flag that runs `boot_db`, skips the socket, walks each in-memory table and
writes one JSON object per line. One generic `SchemaWriteJSON` in
`PRLib/Schema.c` mirrors `CreateOrInitWithSchema`. Players and accounts by
iterating `players.new` / `account.list`.

Alternatives: emitting JSON from `tran` alongside the Ruby dumper (covers only
text sources); a standalone binary reader (reimplements every hand-coded
switch, not worth it).

Caveats: schema tables may omit fields the hand-coded readers fill; cross
references are by vnum; strings with embedded newlines and color codes;
player dumps expose password hashes and emails.

This is outside the Docker packaging remit recorded for the PR, so separate
work.
