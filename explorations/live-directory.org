#+TITLE: live/: what the game reads and writes there
#+OPTIONS: ^:nil

Derived from =src/= (every =fopen/open/opendir/mkdir/rename/unlink/remove/
system/popen/stat= call site, attributed to its caller chain with the
graphify call graph in =graphify-out/graph.json=) plus the shell scripts in
=scripts/= and =world/compile=. The local =live/= tree was *not* used as
evidence. Written 2026-10-08.

See also: [[file:game-engine-loop.org::#periodic][periodic blocks]],
[[file:rooms.org::#saving][room saving]], [[file:mobs.org::#persistence][mob persistence]],
[[file:players.org][players]], [[file:objects.org][objects]].

* How the game reaches live/
:PROPERTIES:
:CUSTOM_ID: layout
:END:

=scripts/PR_SERVER_SCRIPT= runs =live/pr3 -d live/lib ... > live/logs/log 2>&1=
in a loop. =main.c= does =chdir(dir)= to the =-d= directory, and from then on
*every path in the C code is relative to =live/lib=*. So =live/= has exactly
three things: the =pr3= symlink to =src/pr3=, =lib/= (everything the game
touches) and =logs/= (the process's stdout+stderr, touched only by the script).

Nothing in src writes anywhere else on disk. There is no database, no
syslog: =vlog()= in =PRLib/nlog.c= writes to stderr, which the script
redirects to =live/logs/log=.

* One source: live/lib, never the repo
:PROPERTIES:
:CUSTOM_ID: one-source
:END:

The game does not "prefer live over world". It has exactly one source,
=live/lib=, and never reads the world repo, never copies from it, and has
no idea it exists. No path in =src/*.c= contains =world/=, =../=, =ROOM= or
a call to =tran=; every loader opens a bare relative name under the
chdir'd data directory. The only fallback, in =PRLib/misc.c=
=pipe_or_file=, is to run =zcat= on =<name>.gz= in that same directory.

** Missing files
:PROPERTIES:
:CUSTOM_ID: missing
:END:

- *Compiled files are required.* =mob.out obj.out zone.out shop.out
  sector.out race.out clans.out classes actions messages players.new=
  missing → =exit()=. =world.out= missing → logged, boot continues into an
  empty world. Nothing is generated from anywhere.
- *State files are optional.* =main.c= creates =WorldSave/=, =account/= and
  =stash/= itself. No =WorldSave= files → fresh world. No =RoomSave/=,
  =UPDATE/=, admin lists, =BOOT_CLEAN= → logged or silently empty. Missing
  display text → empty string plus =perror=. That is the whole
  start-from-nothing path: compiled files required, state optional.

** How the repo reaches live
:PROPERTIES:
:CUSTOM_ID: repo-to-live
:END:

Only two things do it, both outside the game:
- =world/compile=, run by hand, writes the =.out= files, =classes=, =help=,
  =help_table=, =motd= and the 18 =MISC= files into =live/lib= through the
  =world/lib= symlink. It overwrites unconditionally.
- =scripts/setup_pr_home.sh= runs =world/compile= only if
  =live/lib/world.out= is absent, and restores players from the newest
  =Backups/players_*.tar.gz= only if =stash/= is empty. On a host that is
  already set up it touches nothing.

So the compiled files in live *are* the world as of the last time someone
ran =compile=. The repo can be ahead of production indefinitely and the
game will not notice.

** Continuity on a normal restart
:PROPERTIES:
:CUSTOM_ID: continuity
:END:

=boot_db= order: compiled definitions → =UPDATE/*= overrides → every player
file (=boot_players=) → =LoadWorld= reads and unlinks =WorldSave/*= and
immediately rewrites it → =LoadAutosaveRooms= → =boot_reset=. Saved zone
state is applied on top of the definitions. =boot_reset= (=zone.c=) resets
only zones that are =boot_only= *and* have no save range, or every zone on
a clean boot (=-c=). So:
- a zone with a save range comes back exactly as at its last 10 s save;
- a zone without one is repopulated by its normal reset schedule;
- =-c= (via =BOOT_CLEAN=, which also deletes =WorldSave/=) discards both.

** What this settles for the database
:PROPERTIES:
:CUSTOM_ID: canonical
:END:

Definitions are canonical in the pr-world repo; =live/lib='s compiled
copies are a possibly stale cache and =UPDATE/= an undocumented override
layer. Players, accounts and all runtime state are canonical only in
=live/lib=. Extract definitions from the repo and state from live, with
one caveat: diff =UPDATE/= and the last-compiled =.out= files against the
repo first, so anything production is actually running that the repo
lacks is not lost.

* Who else writes into live/lib
:PROPERTIES:
:CUSTOM_ID: others
:END:

- =world/compile= (the world repo). =world/lib= is a symlink to =../live/lib=.
  It runs =tran= and the per-directory =compile= scripts and copies the
  results in: =world.out mob.out obj.out zone.out shop.out sector.out
  race.out clans.out item_sets.out effects.out skills.out area.list=, plus
  =classes= (CLASSES/), =help=, =help_table=, =motd= (HELP/) and the 18
  files of =MISC/= (=actions messages welcome news credits info donations
  services class_help_info reject_msg pc_is_debtor pc_is_broke login_help
  vote_message newbie_message mxp_elements termcap prompts=). Run by hand;
  nothing in the game triggers it.
- =scripts/pr_functions.sh= =rebuild_indexes= (called by PR_SERVER_SCRIPT on
  every (re)start and by setup): regenerates =players.new= from =stash/=,
  =account.list= from =account/=, =lockers.save= from =LockerSave/=.
- =PR_SERVER_SCRIPT= itself: consumes the =CLEAN_EXIT= and =BOOT_CLEAN=
  marker files; on =BOOT_CLEAN= it =rm -rf WorldSave= and passes =-c=;
  rotates =logs/log= into =logs/recent/log.1..5= and =logs/YYMMDDhhmmss.log=;
  =prune_logs=.
- cron: =backup_players.sh= tars =lib/stash lib/account=;
  =backup_full.sh= tars all of =lib= (minus tarballs, cores, logs);
  =cleanup_core.sh= deletes old =core.*=.
- Nothing writes back to the =world/= repo. The only src→text-world path is
  the builder's =tsave= (below), and that writes under =lib/WORLD/=.

** Display and configuration text: read only, hand edited
:PROPERTIES:
:CUSTOM_ID: display
:END:

All read at BOOT by =file_to_string= in =boot_db=, re-readable with the
=file= command. None is written by src. All of them are copied in by
=world/compile= from =world/HELP= (=motd=, =help=, =help_table=) or
=world/MISC= (everything else), so the repo copy is the master unless
someone edits =live/lib= directly, which =compile= would then overwrite:

=welcome news donations services credits info class_help_info reject_msg
pc_is_debtor pc_is_broke login_help vote_message newbie_message
mxp_elements=; also =termcap= (=init_terms=, BOOT; =file termcap=),
=prompts= (=load_prompt=, read on the =prompt= command), =StoryFiles/<name>=
(read by the =storyteller= mob special when it fires).

=vote_message= is also =stat='ed at boot for its mtime (shown to players as
"new since").

What a zone save contains (=WriteRoom=, for each non-AUTOSAVE room in the
zone's save range): exits whose state differs from default or are
crackable, every mob standing in the room (=SaveMob=: full runtime state),
every object on the floor (=SaveObjectList=), and room flags. AUTOSAVE
rooms are skipped there and go to =RoomSave/= instead, which holds the
same shape of record for a single room.

So the "zone" file is just a batching of per-room records by vnum range;
there is no zone-level state in it.

Consequences:
- Between a =LoadWorld= and the next =SaveZone= round there is a window
  where the only copy of a zone's state is in memory. =LoadWorld= calls
  =full_save_world= immediately, so the window is normally short.
- With =-c= (clean boot) =LoadWorld= is skipped *and* the script has already
  removed =WorldSave/=; the world comes up purely from the compiled files.
- A crash that is not caught by =signal_fatal= loses up to one full
  round-robin cycle (10 s × number of saveable zones) of room/mob/object
  state. The =.room= and locker files are written synchronously on the
  triggering command, so they lose nothing.

| UPDATE/*              | by hand                                                                  | =boot_update= (BOOT): room definitions that override =world.out= | *only in live* |

This is the whole builder→repo path: in-game edits are held in memory and
in =WorldSave= (as changed exits/contents only, not definitions); room
*definitions* only reach disk through =rsave= or =tsave=, and only reach
the repo by hand. Mob and object *definitions* have no in-game write path
at all. Mob and object *placements* do: =load mob= / =load obj= puts an
instance in a room and the zone save carries it across restarts, so a
creative's hand-loaded mobs live only in =WorldSave=, never as a reset
rule in the =.zon= file.

=UPDATE/= is filled only by hand. A copy goes stale as soon as the builder
does =rsave= again, so use a symlink instead: =ln -s ../Area/<builder>
UPDATE/<builder>=. =boot_update= opens entries with =fopen=, which follows
the link, and =rsave= rewrites =Area/<builder>= under the same name, so
the link always points at the latest save.

** Builders: areas, zones, creating rooms, the three saves
:PROPERTIES:
:CUSTOM_ID: builder-model
:END:

*Area vs zone.* An area is a text-file convention: =#define Abyss 25000=
in =world/ROOM/area.list= plus =#offset Abyss= at the top of
=Abyss.room= mean "add 25000 to every room number in this file". That is
its entire job; =tran= adds the base and the running game has no areas.
A zone is a game object: a vnum range, reset schedule and rules, limits,
save range. The two are independent lists that by habit share names and
bases; nothing checks that. Nitemare's rooms (500000+) are in no area and
only in the catch-all =last_room= zone (400000 and up, =reset never=, no
save range).

Cross-file room references are written =Area:n= (that area's base plus
n, e.g. =Midgard:12= = 3012) and =Void:n= when no area covers the target
(=Void= is base 0, so n is the absolute vnum). Changing a base in
=area.list= or an =#offset= line silently moves every room in that file
and every =Area:n= reference to it, while absolute references elsewhere
(player locations, lockers, shops, placements) stay put. Nothing reports
it. The database should carry absolute vnums only.

*Zone overlap.* In the compiled game (129 files in =zone.list=) no two
ranges and no two save ranges overlap. =Nether.zon= (114000-114999,
wrapping five small zones) and =OnikumasClanRooms.zon= are in the repo
but not in =zone.list=, so they are never compiled. A real overlap of
save ranges would be a growing bug: =SaveZone= writes the shared rooms
into both files, =ReadRoom= adds every saved mob without checking, so
mobs double at each restart (objects do not: =ReadRoom= replaces the
room's object list, leaking the first copy). =find_zone= returns the
first zone in list order containing the vnum.

*Creating rooms* (all in memory until =rsave=):
- =rdig <direction>= (I2+, inside the builder's =build_lo..build_hi=,
  stored in their player file and set by an immortal): takes the lowest
  unused vnum in the range, makes a room there named from the direction
  with description "Empty", and wires the exit there and back. The room
  is a side effect of making an exit.
- =goto <vnum>= to a nonexistent vnum (I2+): "You form order out of
  chaos"; creates the room named by its number. This is where *blank
  rooms* come from: name equals vnum. The game's =show= reports runs of
  them as "rooms N-M are blank"; =room2tran= skips them; =tsave= writes
  them.
- =form <lo> <hi>=: creates every missing room in a range, all blank.
=redit= (name, desc, sector, flags, extras, exits/doors/keys/timers,
river, teleport, tracks, delete, swap, =max_people=) edits the room in
memory. It cannot place or define mobs; =load mob= is an instance that
lives only in =WorldSave=.

*The three saves* are one function (=write_room= / =bin_write_room=
over the in-memory room table) with three ways of picking range and
file. None reads another's output; none reads =Area/=, =UPDATE/= or
=world.out=.
- =rsave= (I2): the builder's own range, binary, to =Area/<name>=,
  absolute vnums. =rsave <file> lo hi= (I9) for any range. The reliable
  source; what =scripts/sync_rooms= reads.
- =tsave <file> lo hi= (I9): text, to =WORLD/<file>=, numbered from the
  typed =lo=, no =#offset= line, blank rooms included, exits outside the
  range as =Area:n= / =Void:n=. The file name is never interpreted. Only
  a drop-in for =world/ROOM/<area>.room= when =lo= is exactly the area's
  base and =hi= its end; a smaller range copied whole deletes rooms, a
  larger one duplicates the neighbour's, a wrong =lo= shifts everything.
  Not safe as a manual copy.
- =saveworld= (I10): =tsave= for every area in =area.list= from its true
  base to the next base minus one, plus =WORLD/world= as the include
  list. Never writes the last area, nor anything above the last base.

** logs/
:PROPERTIES:
:CUSTOM_ID: logs
:END:

=logs/log= is the live stdout+stderr of =pr3= (all =vlog= output, command
logging included). Only the script touches it: on each restart it copies
to =recent/log.1= (shifting 1→5) and renames to =YYMMDDhhmmss.log=, then
=prune_logs= keeps the current year or the last three months, whichever is
longer. Excluded from the full backup.

* Redundancy
:PROPERTIES:
:CUSTOM_ID: redundancy
:END:

- *Derived indexes*: =players.new=, =account.list=, =lockers.save= are
  listings of their directories. =players.new= is also appended by the
  game, =account.list= is not (a new account is counted only after the
  next restart's =rebuild_indexes=). =IMMORTALS=, =wizlist=,
  =account.report= are regenerated every boot from the player/account scan.
- *Compiled world and display text* (=*.out=, =classes=, =help*=, =motd=,
  =area.list= and the 18 =MISC= files) duplicate the =world/= repo and are
  regenerated by =world/compile=.
- *Limited-item counts* (=limited.obj=) duplicate what a scan of player
  files and the world would count; the file exists to skip that scan.
- *Room state three ways*: a room's definition lives in =world.out=
  (from the repo), possibly overridden by =UPDATE/*=, possibly re-dumped
  to =Area/= or =WORLD/= by a builder; its *runtime* contents live in
  =WorldSave/zone.N= or, if AUTOSAVE, in =RoomSave/<vnum>.room=. Nothing
  reconciles =Area/=, =WORLD/= and the repo.
- *Mobs*: definition in =mob.out=; every live instance's full state in the
  zone save of whatever room it is standing in. No instance identity, so
  a mob that walked into another zone's range is saved by that zone's
  file next time round.
- *Objects*: prototype in =obj.out=; instances exist in exactly one of
  player file, locker file, room save (zone or RoomSave), or nowhere (if
  carried by a mob that is not in a saved room).
- *Backups*: the player tar covers =stash/= and =account/= only; the full
  tar covers all of =lib=. Everything in the "only in live" column below
  survives only through the full backup.

* What exists only in live/lib
:PROPERTIES:
:CUSTOM_ID: only-live
:END:

Not in any repo, not derivable, and (except the first group) not in the
players tar:

1. =stash/=, =account/= — the player database (players tar, full tar).
2. =WorldSave/=, =RoomSave/=, =LockerSave/= — all runtime room, mob,
   floor-object and locker state (full tar only).
3. =*.board=, =*.auction= — board posts, in-progress auctions.
4. =Area/=, =BUILD.LOG=, =WORLD/=, =TextSave/=, =UPDATE/= — builder work
   that has not been moved into the world repo.
5. =wizlocked no-new always-sites norent disable maxplayers trashcan=
   — admin state.
6. =ideas typos bugs= — player feedback.
7. =StoryFiles/= — storyteller texts; no repo copy.
8. =PURGED/= — deleted characters and accounts, kept for =unpurge=.
9. =logs/= — the only record of commands and events.

A rebuild from the two repos plus the players tar therefore comes up with
a fresh world (no floor objects, no locker contents, no board posts, no
builder edits, default admin lists). Display text, help and the fight
messages all come back from the world repo via =world/compile=.
